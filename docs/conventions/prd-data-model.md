# PRD 数据模型约定

> 状态：草稿，待人工审核。更新日期：2026-11-21。  
> 适用对象：产品负责人、研发、AI Agent。  
> 配套模板：[`docs/templates/产品设计/data-model-template.md`](../templates/产品设计/data-model-template.md)  
> 上位规范：[`prd-writing-guide(AI整理).md`](./prd-writing-guide(AI整理).md) 中的「领域模型」章节。

## 1. 目的

本约定固定一件事：**PRD / 产品侧的「数据模型」表示业务模型（领域概念及其关系），不表示数据库表设计。**

理由：人与 AI 若把「实体」直接写成 `sys_*` 表、列类型、索引，会把产品决策与持久化方案绑死，后续换存储、拆表、加缓存时需求文档被迫跟着改；业务规则应对「用户 / 会话 / 邮箱归属证明」成立，而不是对某一列 DDL 成立。

## 2. 适用范围

必须遵守本约定的文档：

- `docs/product/**` 下标题或文件名含「数据模型」的产品文档（例：`auth_数据模型.md`）
- PRD 正文中的「领域模型 / 数据模型」章节
- 按 [`data-model-template.md`](../templates/产品设计/data-model-template.md) 新建的模型稿

不在本约定范围（技术层自行维护，产品数据模型禁止当作其正文）：

- Liquibase changelog、SQL DDL、索引与分区
- MyBatis `*DO` / `@TableName`、Entity 与 TypeHandler
- Redis / Sa-Token 等运行时键设计的实现细节（业务上可描述「存在共享失败计数」这类**概念**，禁止写成具体 key 模板当产品定案，除非该键形态本身是业务契约）

## 3. 核心定义：业务模型 vs 技术模型

| | 业务数据模型（本约定） | 技术数据模型（实现） |
|--|------------------------|----------------------|
| 回答什么 | 有哪些业务对象、属性、关系、状态、唯一性与级联**业务含义** | 落哪张表、什么列类型、怎么迁移、怎么索引 |
| 命名 | 业务语言：用户、待验证注册、邮箱归属证明 | 物理名：`sys_user`、`varchar(512)`、`uk_user_email` |
| 谁拍板 | 产品 / PRD 确认 | 技术方案 / 研发（可另写 design 或 changelog） |
| 变更触发 | 业务规则或概念变了 | 性能、存储、ORM、加密落地变了 |

必须遵守：

1. **必须**用业务实体名与业务属性名描述模型（中文名 + 稳定英文标识，如 `User` / `EmailRegistration`）。
2. **禁止**把「数据模型」写成以表名为一级标题的库表说明书。
3. **禁止**在产品数据模型中把 DDL、索引名、分库分表、ORM 注解当作需求正文。
4. **允许**在「实现对照 / 现状分析」类附件中**引用**现有表名，且必须标明「对照现状，非业务定案」。
5. 同一业务属性换列类型、改加密落库、拆出附表：**不自动**要求改业务数据模型；仅当业务含义变化时才改。

一句话自检：删掉所有表名与列类型后，业务规则是否仍说得通？说不通，说明写成了技术模型。

## 4. 与其他文档的关系

| 文档 | 写什么 | 与本约定的边界 |
|------|--------|----------------|
| PRD 主文 | 范围、流程、规则、验收 | 领域模型可摘要；细节放到独立「数据模型」文档并互链 |
| 产品「数据模型」文档 | 实体、关系、枚举、业务约束 | 遵守本文；不写 DDL |
| 现状分析 / 实现对照 | 代码与表「现在怎样」 | 可出现表名；禁止把对照结果默认为已批准业务模型 |
| Liquibase / `*DO` | 物理存储 | 由技术方案产出；应对齐已确认业务模型的**含义**，不是反客为主 |
| [`backend-java.md`](./backend-java.md) | 表命名、审计字段等工程约定 | 实现阶段遵守；不替代业务模型 |

## 5. 文档应包含的内容

结构以模板为准，语义必须是业务层：

1. **实体关系**：业务对象之间的 cardinality（1、0..1、0..n），用业务动词描述关系。
2. **实体**：每个业务对象的属性表——含义、是否必填、取值约束（长度、范围、格式、单位）、默认业务值。类型写**业务类型**（标识、文本、枚举、时间、布尔、密文凭证等），禁止把 `int8`/`varchar(64)` 当作产品必填类型，除非该物理形态本身被产品验收（极少见，须在未决中标明）。
3. **枚举**：业务状态与分类的取值及含义。
4. **约束**：业务唯一性（例：租户内登录名唯一）、删除/失效时的业务级联（例：删除用户后会话必须失效），而不是外键 `ON DELETE` 语法。

可选附录（与正文分离）：

- 「实现对照」：现有表/类如何承载上述实体（明确非定案）。

## 6. 写作硬规则

- 必须一词一名：与 PRD 术语表一致。  
- 必须区分「已确认业务概念」与「拟定 / 未决」；拟定项禁止写成已建表事实。  
- 必须写清属性的业务约束（例：口令只存慢哈希结果；注册确认秘密只存哈希）。  
- 禁止用模糊词描述约束（「适当长度」→ 写清边界，或指向 PRD 已确认数字）。  
- 禁止在业务模型中规定「必须用 PostgreSQL / 必须一张表 / 必须 JSON 列」等实现选型，除非 mission/tech-stack 已定为产品硬约束并在 PRD 技术约束章引用。

## 7. 对人与 AI 的执行要求

- 起草产品数据模型时：先列业务实体与关系，再填属性；**禁止**从 `platform-schema.sql` 反推成产品正文。  
- 编码阶段：以已确认业务模型的含义为准设计表结构；表名、列类型、索引在 changelog / 技术方案中产出。  
- 若业务模型与现有表不一致：记入 PRD 未决或实现缺口，**禁止**为迁就旧表而改业务含义而不经人确认。

## 8. 检查清单

- [ ] 正文可以不出现任何物理表名仍完整表达业务对象  
- [ ] 实体名是业务语言，不是 `sys_*`  
- [ ] 属性约束是业务可验收的（谁在什么条件下必须有什么含义）  
- [ ] 无 DDL / 索引 / ORM 注解充作需求  
- [ ] 与 PRD 术语、状态机、业务规则无一词多义  
- [ ] 拟定与已确认已分开标注  
- [ ] 若附了实现对照，已标明「对照 ≠ 定案」

## 9. 存量说明

`docs/product/auth/auth_数据模型.md` 等早期稿可能混有表名与列类型，便于对照现状。后续修订必须：

1. 正文改为业务实体叙事；
2. 表名下沉到「实现对照」附录或现状分析；
3. 未迁移完成前，读者以本约定为准解读「数据模型」一词。
