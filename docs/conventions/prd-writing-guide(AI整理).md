# PRD 编写规范

> 状态：草稿，待人工审核。生成日期：2026-11-19。  
> 适用对象：产品负责人、研发、AI Agent。  
> 配套模板：[`docs/product/_template.md`](../product/_template.md)

## 1. 目的、适用范围、与其他文档的关系

### 1.1 目的

本规范约束「可独立交付的一个功能」如何写成 AI 可执行、人可验收的 PRD，减少 Agent 臆测与人机口径漂移。

### 1.2 适用范围

必须遵守本规范的文档：新建于 `docs/product/<模块>/` 的 `PRD-*.md`。  
历史文档（如 `docs/product/auth/auth_主PRD.md`）见 §11 迁移说明；未完成迁移前禁止以旧格式作为新 PRD 模板。

### 1.3 文档分工（禁止重复）

| 文档 | 写什么 | 禁止写什么 |
|------|--------|------------|
| [`AGENTS.md`](../../AGENTS.md) | Agent 短索引、硬边界、常用命令 | 单功能需求细节 |
| [`docs/mission.md`](../mission.md) / [`roadmap.md`](../roadmap.md) / [`tech-stack.md`](../tech-stack.md) | 使命、阶段、技术硬规则 | 单功能字段与文案 |
| [`docs/architecture/`](../architecture/) | 模块边界与依赖 | 单功能验收用例 |
| [`docs/adr/`](../adr/) `[待建立正文]` | 架构取舍为何如此 | 产品范围取舍全文 |
| [`docs/conventions/`](./) | 跨功能通用规则（分层、异常、UI 范式等） | 本功能特有规则全文复制 |
| **PRD（本文约束）** | 本功能特有：范围、规则、状态机、接口契约、验收、未决 | 通用命名/分层/错误包装全文 |
| [`skills/feature-spec`](../../skills/feature-spec/SKILL.md) | roadmap **阶段**规格三件套 | 与 PRD 重复粘贴同一需求两遍而不互链 |

通用规则只写链接，例如：后端约定见 [`backend-java.md`](./backend-java.md)；前端见 [`frontend.md`](./frontend.md)；页面范式见 [`ui-patterns.md`](./ui-patterns.md)；视觉见 [`frontend/DESIGN.md`](../../frontend/DESIGN.md)。  
正式命名规范 [`naming.md`](./naming.md) `[待建立]`；未建立前，PRD 术语表「代码中的命名」必须与仓库现有类名/表名/路径一致，冲突记入未决问题。

OpenAPI / 契约目录 [`docs/contracts/`](../contracts/) `[待建立]`；原型目录 [`docs/prototype/`](../prototype/) `[待建立]`；安全基线 convention `[待建立]`。

## 2. 核心原则

1. **必须写死会被猜的地方。** 理由：人会补全空白，AI 会直接猜。
2. **每条规则必须可验证，并能转成测试或检查清单。** 理由：不可测等于未定义。
3. **决策由人写；展开可由 AI 起草；检查可由 AI 执行。** 理由：权责分离，避免 AI 替人拍板。
4. **一份 PRD 只对应一个可独立交付的功能；过大必须拆分并写明依赖顺序。** 理由：降低并行改动与回滚成本。
5. **只写本功能特有内容；通用规则必须引用 conventions，禁止复制粘贴大段通用条文。** 理由：避免双源真相。

## 3. 目录与命名

### 3.1 路径与文件名

- 必须放在 `docs/product/<模块>/`，`<模块>` 必须与代码侧业务称呼一致（当前示例：`auth`、`system`、`tenant`、`org`；以 [`repo-map.md`](../architecture/repo-map.md) 与代码目录为准）。
- 文件名必须为：`PRD-<三位序号>-<功能名kebab-case>.md`（例：`PRD-001-email-registration.md`）。
- 序号必须全局递增且禁止复用；新号取现有最大序号 +1（迁移完成前，序号表见 §11）。
- 版本号必须写在文档头元信息，禁止写入文件名；历史以 Git 为准。

### 3.2 文内编号

| 类型 | 格式 | 用途 |
|------|------|------|
| 业务规则 | `<模块>-BR-<两位序号>` | 可判定对错的规则 |
| 异常 | `<模块>-EX-<两位序号>` | 异常分支与对外表现 |
| 验收 | `<模块>-AC-<两位序号>` | Given-When-Then |
| 未决问题 | `<模块>-Q-<两位序号>` | 人必须拍板的问题 |
| 用户故事（可选嵌套） | `US-<模块缩写>-<序号>` | 与 [`docs/README.md`](../README.md) 一致 |

模块前缀示例：`auth`、`user`、`tenant`、`org`。  
同一概念全文必须只用一个名字；术语表「代码中的命名」必须与实体/表/接口路径一致。

### 3.3 与 feature-spec 目录的关系

- roadmap **阶段**规格三件套路径为 `docs/product/YYYY-MM-DD-<slug>/{requirements,plan,validation}.md`（见 feature-spec skill）。
- 功能 PRD 与阶段规格必须互链：阶段 `requirements.md` 必须列出依赖的 `PRD-*` 路径；PRD 元信息必须填写关联 roadmap 阶段（若有）。
- 禁止把同一验收标准在两处写成互相矛盾的两套正文而不标注以哪份为准。  
（二者并存策略若需调整，见人工待确认项，本文不擅自取消任一侧。）

## 4. PRD 结构与各章填写要求

不涉及的章节必须保留标题并写「不涉及」，禁止删除章节。  
**范围外、异常流程、验收标准、未决问题**四章禁止省略内容（可写「不涉及」仅当确实无该项，且验收/未决不得用空章敷衍：验收至少覆盖已声明范围内的四类场景；无未决必须写「无」）。

| 章 | 必填 | 用途 | 写法要求 | 常见错误 |
|----|------|------|----------|----------|
| 元信息 | 是 | 状态、版本、负责人、依赖 | 用模板表；状态仅允许 §7 枚举值 | 状态写「基本完成」 |
| 0. 给 AI 的执行说明 | 是 | 约束 Agent 行为 | 写明两阶段、只读已确认 PRD 才编码、链到 AGENTS/conventions | 让 AI「自行发挥」 |
| 1. 背景与目标 | 是 | 为何做、做成什么样 | 可观察结果；对齐 mission/roadmap | 空喊「提升体验」 |
| 2. 范围（含范围外） | 是 | In/Out | 用条目；范围外单独列表 | 只写要做什么 |
| 3. 术语表 | 是 | 中文↔代码标识 | 含类/表/路径；一词一名 | 中英混用多名 |
| 4. 角色与权限 | 是 | 谁能做什么 | 角色×动作矩阵或等价表 | 「管理员可以管理」 |
| 5. 领域模型 | 是 | 字段、关系、状态机 | 字段约束用数字；状态机无死路 | 只贴 ER 无约束 |
| 6. 业务流程 | 是 | 主/分支/异常 | 步骤可执行；异常指向 EX | 只画开心路径 |
| 7. 业务规则 | 是 | BR 列表 | 每条可测；引用数字与示例 | 「合理校验」 |
| 8. 页面与交互 | 条件 | UI 特有 | 引用 ui-patterns/DESIGN；只写差异 | 重写整套设计系统 |
| 9. 接口契约 | 条件 | 本功能 API | 方法、路径、字段、错误码与文案 | 「参考现有接口」 |
| 10. 非功能要求 | 是 | 性能/可用性等 | 阈值、耗时、并发用数字 | 「尽快响应」 |
| 11. 技术约束 | 是 | 红线与依赖 | 只写本功能增量；通用硬规则链 tech-stack | 复述整份 tech-stack |
| 12. 验收标准 | 是 | AC 四类场景 | Given-When-Then；正常/边界/异常/权限 | 只有正常路径 |
| 13. 样例数据 | 条件 | 可准备的数据 | 可直接构造的值 | 「若干测试用户」 |
| 14. 未决问题与假设 | 是 | Q 与假设 | 未决必须选项化；假设标明若推翻的影响 | 把推荐写成已批准 |
| 15. 变更记录 | 是 | 已确认后的变更 | 版本、日期、变更点、影响面 | 只改正文不记变更 |
| 16. 安全与威胁场景 | 条件 | 高风险功能 | 见 §10；认证/权限/导出删除等必须有 | 高风险功能缺失 |

「条件」：无 UI 则第 8 章写「不涉及」；无新/改 API 则第 9 章写「不涉及」；非高风险则第 16 章写「不涉及」。

## 5. 写作要求

### 5.1 禁止使用的模糊词

| 禁止词 | 必须改成 |
|--------|----------|
| 合理 / 适当 | 写出具体阈值、枚举或算法（例：口令 8–32 字符，至少 1 小写 + 1 数字） |
| 尽快 / 及时 | 写出 SLA（例：p95 ≤ 200ms；邮件 5 分钟内送达为运维目标并标明是否验收） |
| 较大 / 较多 / 较高 | 写出比较基准与数字（例：中位数之比 ≤ 1.5） |
| 必要时 / 视情况 | 写出触发条件布尔表达式 |
| 等等 / 相关 / 等 | 改为穷举列表或「仅含下列 N 项」 |
| 完善 / 优化体验 | 改为可观察行为与验收 AC |
| 参考现有实现 | 写明路径/接口/表名，或改为未决问题 |

### 5.2 其他硬性写法

- 规则必须带具体数字或封闭枚举。理由：否则无法写测试。
- 同一概念全文必须只用术语表中的一个名字。理由：避免前后端各说各话。
- 示例数据、对外报错 `code` 与 `message` 文案必须写出，禁止只描述「返回错误」。理由：文案与枚举防探测常被 AI 改坏。
- 「推荐」不等于「已确认」；未确认项必须进入未决问题，禁止写成可执行默认步骤。理由：现有 auth 主 PRD 已证明该区分必要。

## 6. 人与 AI 的分工

### 6.1 必须由人写或拍板

背景目标、范围取舍、权限策略、核心业务规则、状态机关键流转、安全数值、非功能指标、技术红线、未决问题结论、验收最终确认。

### 6.2 AI 可起草、人必须审

领域模型细节、异常清单、验收用例草稿、页面细节、接口契约草稿、错误码与文案草稿、术语表、样例数据。

### 6.3 AI 执行的检查（定稿前）

找矛盾、找遗漏、找模糊词、以工程师身份列疑问、复述理解（提示词见附录 C）。

### 6.4 判断问句

「这里写错了，AI 能自己发现吗？」若不能，则必须由人写并确认。

## 7. 协作流程与状态流转

### 7.1 状态

仅允许：`草稿` → `评审中` → `已确认` → `已过期` 。  
**禁止**在状态非 `已确认` 时让 AI 按该 PRD 改业务代码、库表或生产配置。理由：未确认需求不是实施授权（与现有 auth 主 PRD 声明一致）。

### 7.2 两阶段执行

1. **阶段一**：AI 输出理解确认、技术方案（表/接口/任务拆分）、疑问清单；人确认后进入阶段二。
2. **阶段二**：按已确认 PRD + 技术方案编码与补测。

PRD 未覆盖的情况：AI 必须提问或写入假设清单，**禁止自行决定**。  
验收编号必须在测试代码注释或测试名中引用（例：`auth-AC-03`），保证需求到测试可追溯。

## 8. 评审与定稿检查清单

- [ ] 范围与范围外均已列出；无「等等」
- [ ] 主流程、分支、异常均有对应 EX 或步骤
- [ ] 每条 BR 可写成断言；无模糊词（对照 §5.1）
- [ ] 术语表一词一名；代码命名与仓库一致或已开 Q
- [ ] 角色×动作完整；无隐含「超级权限」
- [ ] 状态机无死路、无未定义跳转
- [ ] 验收覆盖：**正常 / 边界 / 异常 / 权限** 四类
- [ ] 高风险功能已含 §10；安全数值为人确认
- [ ] 元信息状态、版本、依赖 PRD 已填
- [ ] 通用规则仅链接 conventions，无大段复制

## 9. 变更管理

已确认 PRD 修改必须：

1. 将状态改回 `评审中`（或新开修订版本号并保持可追溯）。
2. 在「变更记录」写明：变更点、原因、影响的代码模块/接口/表/测试/AC。
3. 人确认后改回 `已确认`。
4. 若变更触及范围、权限、状态机或安全数值：必须要求 AI **重新执行阶段一** 再编码。

禁止静默改已确认正文而不更新变更记录。

---

## 10. 高风险功能补充要求

适用范围（满足任一即必须启用第 16 章）：认证与会话、支付与资金、权限与租户隔离、批量数据导出或删除、验证码/OTP、密钥与凭证发放。

必须包含：

1. **反向规则（禁止项）**：例：禁止用响应差异做账号枚举；禁止口令/验证码原文入日志与 URL 查询串；禁止验证码在响应中回显。
2. **安全策略数值表**：锁定阈值、窗口、限流、有效期等；数值必须由人确认。
3. **攻击与边界验收**：至少覆盖枚举、重放、并发消费、跨租户头篡改等与本功能相关的场景。
4. **人工评审门禁**：AI 生成的相关代码禁止未经人工评审合并/上线。

安全基线文档 `[待建立]`；在建立前，高风险 PRD 必须自带完整禁止项与数值表，禁止写「按公司安全规范执行」而不列数字。

## 11. 现有文档迁移说明

| 现状 | 与本规范差异 | 迁移要求 |
|------|--------------|----------|
| `docs/product/auth/auth_主PRD.md` 等 | 文件名非 `PRD-NNN-kebab`；规则号为 `R*`/`D-*`/`T*`；章节自研 | 新变更优先按本规范开新文件或改名；旧 ID 在术语/映射表中保留对照，禁止沉默改义 |

## 附录 B. 示例片段（取自仓库认证场景）

### B.1 业务规则片段

- `auth-BR-01`：公开注册请求体字段必须仅为 `email`、`password`；禁止要求用户名。  
- `auth-BR-02`：注册受理成功对外必须统一 `HTTP 200`、`code=200`、文案含「注册申请已受理…」；禁止返回可用于探测邮箱是否已注册的字段。

### B.2 状态机片段（账号）

`待验证` →（确认成功）→ `正常`；`正常` →（禁用）→ `禁用`；`正常` →（失败达阈值）→ `临时锁`（到期回到可登录判定）。禁止在「口令未证实」时对外区分「不存在 / 错密码 / 禁用」。

### B.3 验收片段

- `auth-AC-01`（正常）Given 注册开放且邮箱无账号。When 提交合法邮箱与符合策略口令。Then `HTTP 200` 且无 token，且无 `delivered`/`PENDING`/`COOLDOWN` 探测字段。  
- `auth-AC-02`（异常）Given 标识不存在与口令错误与「禁用且口令错」。When 各登录一次。Then HTTP 状态、业务 `code` 与 message 三者相同。

（完整规则以 `docs/product/auth/auth_主PRD.md` 为准；上例仅示范写法。）
