# 任务：编写《PRD编写规范》

## 目标
编写一份面向"人 + AI Agent 协作开发"的PRD编写规范，输出：

1. `conventions/prd-writing-guide(AI整理).md`：规范正文

3. 如认为 `AGENTS.md` 需要增加指引，只在回复中给出建议的修改内容，不要直接改

## 硬性约束
1. 除上述输出文件外，不修改仓库内任何文件，不执行改变状态的命令。
2. **先读后写**：先完成"第一步"，再动笔。
3. **与现有规范一致**：不得与 `AGENTS.md`、`conventions/`、`tech-stack.md`、`architecture/` 已有内容冲突；发现冲突，记入回复中的"待确认问题"，不要擅自选边。
4. **不重复通用规则**：命名、分层、日志脱敏、统一错误响应等已在 `conventions/` 中的，规范里只写引用链接，不复制内容。
5. 规则一律用"必须 / 禁止"，不用"建议 / 尽量"；每条规则附一句理由。
6. **不编造**仓库中不存在的目录、文件、工具；规范要求但仓库尚未存在的，标注 `[待建立]`。
7. 规范正文控制在约400行以内（AI要读取）；模板、示例、自检提示词放附录或独立文件。
8. 文档头标注：`状态：草稿，待人工审核`。

## 第二步：规范必须覆盖的内容（设计要求）

### 1. 目的、适用范围、与其他文档的关系
说明PRD与 `AGENTS.md`、`conventions/`、`adr/`、`architecture/`、`openapi.json` 的分工：通用规则放 conventions，PRD只写本功能特有内容。

### 2. 核心原则
- 人会靠经验补全空白，AI会直接猜：凡是会被猜的地方必须写死
- 每条规则必须可验证，能转成测试
- 决策由人写，展开由AI起草，检查由AI执行
- 一份PRD只对应一个可独立交付的功能，过大则拆分并写明依赖顺序
- 只写本功能特有内容，通用规则引用 conventions

### 3. 目录与命名
- 文件名：`PRD-<三位序号>-<功能名kebab-case>.md`，序号全局递增不复用
- 按业务模块分子目录，模块名与代码模块名一致
- 版本号写在文档头元信息中，不放文件名，历史交给Git
- 文档内编号加模块前缀：`<模块>-BR-xx`（业务规则）、`-EX-xx`（异常）、`-AC-xx`（验收）、`-Q-xx`（未决问题）
- PRD术语表中的"代码中的命名"必须与实体类、表名、接口路径一致，引用 conventions 的命名规范

### 4. PRD结构与各章节填写要求
章节：元信息、给AI的执行说明、背景与目标、范围（含范围外）、术语表、角色与权限、领域模型（字段、关系、状态机）、业务流程（主流程、分支、异常）、业务规则、页面与交互、接口契约、非功能要求、技术约束、验收标准、样例数据、未决问题与假设、变更记录。

对**每一章**写明：用途、必填还是可选、写法要求、一个常见错误写法。
不涉及的章节必须写"不涉及"，不允许直接删除。
**范围外、异常流程、验收标准、未决问题**四章不得省略。

### 5. 写作要求
- 给出"禁止使用的模糊词"清单（如：合理、尽快、较大、适当、必要时、等等、相关），每个附可验证的替代写法
- 规则用具体数字和示例
- 同一概念全文只用一个名字
- 示例数据和报错文案优先于大段描述

### 6. 人与AI的分工
- 必须由人写：背景目标、范围取舍、权限策略、核心业务规则、状态机关键流转、安全数值、非功能指标、技术红线、未决问题结论、验收最终确认
- AI起草人审：领域模型细节、异常清单、验收用例、页面细节、接口契约、错误码与文案、术语表、样例数据
- AI执行的检查：找矛盾、找遗漏、找模糊词、以工程师身份提问、复述理解
- 判断问句：这里写错了，AI能自己发现吗？不能则必须由人写和确认

### 7. 协作流程与状态流转
- 状态：草稿 → 评审中 → 已确认；**只有"已确认"的PRD才允许AI进入编码**
- 两阶段：阶段一输出理解确认、技术方案（表结构、接口、任务拆分）、疑问清单，人确认；阶段二再编码
- PRD未覆盖的情况，AI必须提问或写入假设清单，禁止自行决定
- 可追溯：验收用例编号在测试代码中引用，需求到测试可追溯

### 8. 评审与定稿检查清单
可勾选的清单，覆盖：范围完整、异常覆盖、规则可验证、无模糊词、术语一致、权限完整、状态机无死路、验收覆盖四类场景（正常、边界、异常、权限）。

### 9. 变更管理
已确认后的修改流程、变更记录要求、影响分析（涉及哪些代码、测试、接口）、变更后是否需要让AI重新评估。

### 10. 高风险功能补充要求
适用范围：认证、支付、权限、数据导出或删除等。必须额外增加"安全与威胁场景"章节，包含：
- 反向规则（必须写成"禁止"，如防账号枚举、敏感信息不入日志不入响应、验证码不在响应中返回）
- 安全策略的具体数值表（锁定、限流、有效期等，由人决策）
- 攻击与边界场景的验收用例
- 必须人工评审的环节（AI生成代码不得未经评审上线）
引用 `conventions/` 中的安全基线文档（不存在则标注 `[待建立]`）。

### 附录
- **A. 模板位置**与使用说明
- **B. 示例片段**：用仓库中已有的业务场景（没有则用通用的"订单退款"，并标注为示例），只展示业务规则、状态机、验收用例各一段，不要写完整PRD
- **C. PRD自检提示词**：可直接复制给AI，让它按"找矛盾、找遗漏、找模糊词、以工程师身份列疑问、复述理解"五项检查一份PRD并输出问题清单
- **D. PRD执行提示词**：可直接复制给AI，分阶段一（理解确认与技术方案）和阶段二（编码与测试），写明交付物和遇到未覆盖情况的处理方式

## 第三步：输出模板
